Extension ↔ Backend Integration Spec

For: Extension team (PS 26171) Covers: Exactly what to send, when, and what you get back. Redaction mechanics are your call — this only covers the contract with the backend.

1. Your numbered-marks approach already fits the schema

The numbered boxes you're already overlaying (see the Wikipedia example — [0] hamburger menu, [2] donate, [18] profile image, etc.) map directly onto the mark_id field the backend expects. You don't need to change your marking scheme at all — just make sure the number burned into the screenshot for a given element is the exact same mark_id you send in that element's JSON entry. That correspondence is the whole trick that lets the backend reason about a screenshot and a DOM list as the same thing.

(Named mark_id rather than id on purpose — it avoids colliding with the element's own native DOM id attribute, which is a different thing and not something the backend needs at all.)

One rule this depends on: mark_ids must stay stable for an element across snapshots. If element 18 (the profile photo) is still the profile photo next screenshot, it must still be mark_id: 18 — don't renumber from scratch each capture, or the backend's action journal and diffing both break.

2. Four endpoints, one session

All requests are POST with a JSON body, all responses are JSON. One session_id (generate a uuid when a task starts, reuse it for every call in that task) ties everything together.

Endpoint When to call it
POST /task/start Once, when a new task begins
POST /task/step After you've executed an action and the DOM has changed
POST /task/screenshot After the backend specifically asked for a screenshot
POST /task/stop?session_id=... The user cancels — this wipes the session server-side

Only ever one in-flight call per session at a time. Wait for the response before sending the next one — the backend is a strict request → one-action → response loop, not a stream.

3. The snapshot shape (same structure for start/step/screenshot)

{
  "session_id": "abc-123",
  "task": "Search 'Nodejs' on Google and open the Wikipedia result.",
  "snapshot": {
    "session_id": "abc-123",
    "step": 4,
    "elements": [
      {
        "mark_id": 18,
        "tag": "img",
        "role": "img",
        "text": null,
        "value": null,
        "redacted": true,
        "redaction_reason": "contains_face"
      },
      {
        "mark_id": 21,
        "tag": "a",
        "role": "link",
        "text": "Portugal national team",
        "value": null,
        "redacted": false
      }
    ],
    "changed_since_last_step": [18],
    "screenshot_available": true,
    "screenshot_b64": null
  }
}

Field notes:

  • elements — only elements currently visible in the viewport. Never send off-screen elements, even if you've already scanned them — that's a hard rule, not an optimization. If the model needs something off-screen, it'll call scroll and you'll send a fresh snapshot after.
  • mark_id — stable per-element, as above.
  • redacted / redaction_reason — however your redaction stage classifies it; the backend just needs the boolean + a short reason string ("contains_face", "password", etc.). Leave text/value as null or a placeholder when redacted: true — never send the real content alongside the flag.
  • changed_since_last_step — list of mark_ids whose text/value/redaction differs from the previous snapshot you sent. This is what tells the backend an action actually did something — get this right, it's load-bearing for the whole loop.
  • screenshot_available — just true/false, whether you could capture one right now. Never send actual image bytes here — only in the dedicated /task/screenshot call (next section).
  • screenshot_b64 — always null except in the one call where you're actually delivering a requested screenshot.

4. The response you get back

{
  "session_id": "abc-123",
  "status": "running",
  "action": {
    "type": "click",
    "target_id": 21,
    "text": null,
    "direction": null,
    "summary": null
  },
  "summary": null
}

status is one of "running", "done", "failed". action.type is one of:

type What you do
click Click the element with this target_id (refers to that element's mark_id)
type_text Type text into the element with this target_id (refers to that element's mark_id)
scroll Scroll direction ("up"/"down") — no target element
request_screenshot Don't touch the DOM. Capture + redact a screenshot, send it via /task/screenshot
summarize_page / task_complete Terminal — status will be "done". Show summary to the user. Nothing to execute.

Only ever one action per response. Execute it, capture the resulting DOM state, send the next call. Never batch multiple actions before responding.

5. The screenshot round trip, specifically

  1. You get back action.type == "request_screenshot".
  2. Do not send a new DOM snapshot for this — the DOM hasn't changed, you're just supplying a picture of what's already there.
  3. Capture the screenshot (with your numbered marks already burned in, as usual), run your redaction pass on the pixels (blur faces, black out sensitive regions), base64-encode it.
  4. POST /task/screenshot with:
    • the same elements list you last sent (nothing changed)
    • changed_since_last_step: []
    • screenshot_b64 set to the raw base64 string — no data:image/png;base64, prefix, just the encoded bytes themselves
  5. You'll get back a normal action response, same as any other step.

6. Stopping mid-task

If the user cancels or closes the flow before the task reaches "done"/"failed", call:

POST /task/stop?session_id=abc-123

No body needed. This tells the backend to drop everything it's tracking for that session — do this every time the user cancels, not just on tab close, since a stale session left alive server-side is what causes a late/duplicate action if the user starts a new task with a reused session_id by accident. Always generate a fresh session_id for a new task rather than reusing an old one.

7. What NOT to do

  • Don't renumber element mark_ids between snapshots.
  • Don't send off-screen elements.
  • Don't send screenshot bytes anywhere except /task/screenshot.
  • Don't fire a second request before the previous one's response comes back.
  • Don't skip /task/stop on cancel — a dangling session is a bug, not a no-op.
  • Don't try to execute more than the single action you were given.
